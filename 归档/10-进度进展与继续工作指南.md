## 三、继续工作行动卡（按优先级排序）

> 每张卡自包含：目标 / 前置 / 步骤 / 验收 / 涉及文件。**A 类（外部条件类）优先做**——它们代码已就绪，只差配置，且每张卡 1~2 小时即可收口一个"doing"。

### 卡 A-1【最高优先】回填 7 个验证器的 valid 实证

- **目标**：把 T4.2 从 doing 推到 done；把评价 2 的"验证能力"数字从 8 类接入升级为 8 类双例实证。
- **前置**：各平台的自有测试凭据（必须是**你自己有权测试的**）：Gitee 私人令牌 / GitLab PAT / Slack token（xoxb- 测试用）/ Telegram Bot Token / npm publish token / HF token / AWS AK+SK 配对。**没有的平台跳过，不必凑齐。**
- **步骤**：
  1. 启动系统（归档/05 §1.2）→【设置】页没有对应输入框的平台，用 Python 直连 API：`httpx.post("http://127.0.0.1:8000/api/findings/{id}/verify", ...)`；
  2. 更直接的方式：造一条对应类型的假凭据导入（examples/demo_repo 模式）→ 发现列表找到它 → 点验证——注意这测的是 invalid 路径（已有）；**valid 路径需要"真凭据"**：在设置库手工插入一条 encrypted 记录或写 10 行脚本直接调 `verification.worker` + 真实凭据（参考 DEVLOG 中 GitHub valid 的做法：`data/github.token` 模式）；
  3. 逐平台记录：HTTP 状态码、返回语义（valid）、latency_ms。
- **验收**：docs/EVALUATION.md §4 新增小节"验证器 valid 回填"，逐平台一行证据（平台/端点/状态码/时延）；test_verification_phase4 不需要改（映射已有）。
- **涉及文件**：docs/EVALUATION.md、docs/DELIVERABLES.md（评价 2 数字更新）、docs/SUPPORT_MATRIX §三、backend/tests/（如加脚本则放 scripts/）。
- **红线**：只用自有凭据；证据不写凭据本身，只写端点+状态码+时延。
