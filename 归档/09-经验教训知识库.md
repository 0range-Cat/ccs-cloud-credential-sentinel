# 09 · 经验教训知识库（踩坑全记录）

> 归档时间：2026-10-08。本文把项目开发全程的踩坑按"症状 → 根因 → 解决 → 预防"结构整理成可检索的知识条目，共 24 条，分五类。每条都对应真实发生过的错误（DEVLOG 可查证），不是理论风险。接手者遇到相似症状时先查本文。

---

## A. 框架与异步类

### A1. 验证器"注册了类而不是实例"
- **症状**：运行验证时 TypeError，调用栈指向注册表。
- **根因**：`register` 装饰器把类对象本身当实例放进注册表。
- **解决**：装饰器改为传类自动实例化。
- **预防**：注册语义统一收口在 base.register；新增验证器不允许绕过装饰器注册。

### A2. API 事件循环内调用 asyncio.run 报错
- **症状**：在 API 请求上下文里同步触发扫描 → RuntimeError（循环已在运行）。
- **根因**：asyncio.run 不能嵌套在已有事件循环的线程里。
- **解决**：`pipeline._run_async` 探测当前线程循环——worker 线程直接 run；API 上下文另起单线程池。
- **预防**：任何"同步入口驱动异步代码"都走 `_run_async`，不要直接 asyncio.run。

### A3. 手动触发扫描"发现数 0"（语义冲突）
- **症状**：点立即运行，任务被跳过，无报错。
- **根因**：`trigger_manual_run` 触发时先置 running，与 `run_task` 的防重叠检查冲突。
- **解决**：触发不置状态，统一由 run_task 领取（两级防重叠语义理顺）。
- **预防**：状态变更只允许一个入口；"触发"与"执行"分属两层。

### A4. worker.http_factory 返回"工厂的工厂"
- **症状**：mock 测试全绿，首次**真实**验证调用 TypeError。
- **根因**：http_factory 返回的是创建客户端的函数，验证器契约要求"返回即客户端"。
- **解决**：修正为返回即客户端实例。
- **预防**：**mock 测试覆盖不了"接线"错误**——真实验收不可替代；关键接缝应有契约级断言。

### A5. BaseCollector 缺 rate_limited 默认属性
- **症状**：流水线 internal_error。
- **根因**：新增采集器忘记初始化 `rate_limited` 标志。
- **解决**：BaseCollector 类级默认 `rate_limited = False`。
- **预防**：契约字段给默认值，别指望每个实现者记得。

## B. 平台行为类

### B1. 维基媒体拒通用 UA（403）
- **症状**：curl 200 但 httpx 请求 403，MediaWiki 首轮实采 0 条。
- **根因**：维基媒体对默认/通用 UA 有策略拒绝。
- **解决**：内置描述性合规 UA（含联系方式），统一常量 base.USER_AGENT（D10）。
- **预防**：采集器一律用统一 UA 常量，禁止裸创建 httpx 客户端。

### B2. MediaWiki formatversion=2 修订对象无 revid
- **症状**：UA 修复后仍 0 条——内容映射全空。
- **根因**：formatversion=2 的修订对象结构与文档直觉不符（无 revid 字段）。
- **解决**：按 pageid 映射；测试锁定。
- **预防**：对第三方 API 的响应结构以实测为准，不按直觉写映射。

### B3. Stack Overflow quota_remaining:0 的 falsy 陷阱
- **症状**：配额耗尽判断永不触发。
- **根因**：`x or 1` 把 0 也当 falsy 吞掉。
- **解决**：显式 `is None` 判断；测试锁定。
- **预防**：数值型配额/计数判断禁用 `or` 短路。

### B4. Docker Hub blob 307 重定向到 CDN
- **症状**：OCI 采集 blob 拉取失败。
- **根因**：Docker Hub 把 blob 请求 307 到 CDN 域名。
- **解决**：**采集层** follow_redirects=True；**验证器仍严格禁重定向**。
- **预防**：两个模块的重定向语义刻意不同（已在模块边界铁律成文）——改动前先读边界。

### B5. GitHub fine-grained PAT 默认无 Contents:write
- **症状**：PUT contents 全部 403（"Resource not accessible by personal access token"），尽管界面显示 push/admin true。
- **根因**：fine-grained Token 细粒度权限与仓库角色显示不一致。
- **解决**：权限探测先行（/user + PUT 探测）；配置需求明确写入文档。
- **预防**：做写操作前先做最小写探测，别信界面显示。

### B6. GitHub push protection 拦截合成凭据
- **症状**：推送合成 Twilio SID 被"Secret detected"拒绝；ghp_ 假值反而不拦（校验位校验）。
- **根因**：GitHub secret scanning 对高逼真格式凭据强制拦截。
- **解决**：官方 bypass API（POST /repos/{o}/{r}/secret-scanning/push-protection-bypasses，reason=used_in_tests）；流程固化进 latency_experiment.py；2026-10-08 归档推送再遇同题，分两批 bypass 10 个 placeholder 后成功。
- **预防**：向 GitHub 推送含测试凭据格式的内容前预留 bypass 流程；**注意：每推一次才会暴露下一批 placeholder ID，需要循环"推送→收集→bypass→再推"**。

## C. 数据与编码类

### C1. alembic.ini 中文注释 GBK 崩溃
- **症状**：Windows 控制台跑 alembic → UnicodeDecodeError。
- **根因**：GBK 控制台 + 配置文件中文注释。
- **解决**：alembic.ini 保持纯 ASCII。
- **预防**：构建链路上的配置文件一律 ASCII；中文放代码注释/文档。

### C2. Git Bash curl 中文 JSON 乱码
- **症状**：curl 发中文 body 服务端收到乱码。
- **根因**：Windows 控制台 GBK 编码。
- **解决**：改用 Python 客户端或界面操作。
- **预防**：Windows 下 API 调试避免 curl+中文组合。

### C3. 时区 aware/naive 混用
- **症状**：latency 实验脚本报时区比较异常。
- **根因**：datetime aware 与 naive 混合比较。
- **解决**：统一 aware UTC 后再比较；全库约定 naive UTC（utcnow）。
- **预防**：时间字段入库前统一经 utcnow()；实验脚本对外时间一律 timezone-aware。

## D. 解析与安全类

### D1. OCI whiteout 层序应用错误
- **症状**：测试发现 `in_final_view` 计算不符容器语义。
- **根因**：初版把删除标记作用顺序写反。
- **解决**：最终视图 = 按层序"先应用下层删除标记，再叠加本层文件"；测试断言锁定。
- **预防**：涉及分层语义（容器/补丁类）先写层序测试再写实现。

### D2. wxapkg 条目 offset 相对正文起点
- **症状**：解析出的内容错位。
- **根因**：偏移基准理解错误。
- **解决**：修正为相对正文起点；三级越界校验（索引/正文/条目）。
- **预防**：二进制格式先画偏移基准图；每个字段一个越界断言。

### D3. APK PK 头校验 `len>4` 笔误
- **症状**：某些 zip 误判。
- **根因**：边界比较写错。
- **解决**：修正并测试锁定。
- **预防**：魔数/长度校验的边界值写显式测试。

### D4. 压缩包路径穿越与解压炸弹
- **症状**：无（设计期防御，未发生事故）。
- **根因**：zip/tar 的绝对路径与 `..` 段、符号链接、超大成员都是已知攻击面。
- **解决**：`_entry_safe` 拒绝穿越；tar 跳过链接/设备；512MB 总量熔断；成员数/单成员上限。
- **预防**：所有"解包"类采集器复用同一套熔断常量与检查函数。

### D5. 加密小程序包（V1MMWX）
- **症状**：无（合规设计）。
- **根因**：解密加密包 = 绕过平台访问控制。
- **解决**：检测到 V1MMWX 魔数明确拒绝，拒绝路径有测试。
- **预防**：合规边界写成代码路径 + 测试，而不是口头约定。

## E. 流程与口径类

### E1. mock 测试的覆盖盲区（A4 的流程面）
- **教训**：阶段 1 全绿 → 阶段 2 首次真实 GitHub 验证即崩（http_factory 形状错误）。
- **预防**：每个"测试全绿"后必有一次真实服务冒烟；live 验收独立于单测，不可省略。

### E2. "发现数 0"的两类原因要分清
- **教训**：同样的表象（0 发现），一次是语义冲突（A3），一次是 UA/映射（B1/B2）。
- **预防**：排查 0 发现先看批次统计（items_seen/skipped/stop_reason）——是没采到、采到没检、还是检到没入库，三段定位。

### E3. 口径漂移风险
- **教训**：GitHub 从 offline_tested 升 live_verified 时，旧测试断言仍在断言旧状态。
- **解决**：状态演进时同步更新断言（有意为之——测试即口径的守护）。
- **预防**：状态口径变更 = 文档 + 能力清单 + 测试三处同改。

### E4. Token 生命周期管理
- **教训**：实验用 Token 在聊天中出现（无法收回）；吊销后种子扩展 live 验证被动搁置。
- **预防**：Token 出现在任何对话/文档中即视为"需轮换"；依赖用户 Token 的验证项要预留"mock 锁定 + 待补 live"的中间态。

### E5. pytest 输出经管道可能吞关键行（2026-10-08 新增）
- **症状**：`pytest -q | grep passed` 拿不到汇总行（exit=0 但无 passed 行）。
- **根因**：输出缓冲与管道时序差异。
- **解决**：直接跑 `python -m pytest` 取末行汇总。
- **预防**：验证类命令避免再套 grep 管道取关键结论行。
